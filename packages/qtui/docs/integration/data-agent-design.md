# qtoc_core 数据治理领域智能体：需求与设计（宏观）

> 定位：在**不 fork 内核、最小 delta、可持续同步 OpenCode 上游**的前提下，把 `qtoc_core` 扩展为面向数据分析、数据治理与数据语义化查询（Text-to-SQL）的领域智能体运行时。
> 本文聚焦**宏观设计**（架构、边界、能力需求、流程与兼容策略）；实施细节（工具 Schema、提示词、评测集）在后续设计文档中展开。
> 版本基线：opencode `1.18.32`（channel `qt-headless`）。
> 关联文档：`../guide/qt-shell-guide.md`（客户端接入）、`methodology.md`（集成方法与决策）、`implementation.md`（实施步骤）、`../api/qtoc-http-api.md`（协议清单）、`../KG/data-agent-faq.md`（扩展边界与交付形态决策）。

---

## 1. 目标、范围与非目标

### 1.1 目标

1. 让 `qtoc_core` 在保持现有架构与上游同步能力的前提下，承载**数据治理领域智能体**（Text-to-SQL、数据质量检查、元数据/血缘问答、治理规则生成等）。
2. 以一条真实链路为样板：**业务描述 → SQL 生成 → 校验/执行 → 固定格式输出 → 格式与质量检查 → 不合格则修复重查**，形成可复制的领域适配方法论。
3. 领域能力以**外部网关 + 配置 + 插件**实现，内核仅使用稳定的扩展点；上游升级不导致返工。

### 1.2 范围

- 领域智能体的能力分层、职责边界、扩展点选型与兼容策略；
- Text-to-SQL 样例链路的宏观流程、失败分类与修复回路；
- 安全、审计、多租户、部署与演进路线；
- 与 Qt 壳、业务服务、数据平面的接口约定（宏观契约）。

### 1.3 非目标（本期不做）

- 不修改内核的会话/工具/权限主流程，不新增内核内置工具；
- 不实现具体 SQL 方言解析器、规则引擎与调度器（属于外部服务实现）；
- 不定义完整 UI 交互（由 Qt 壳承担，参见 `../guide/qt-shell-guide.md`）；
- 不做模型微调（先以提示工程 + 检索 + 确定性工具达成目标）。

## 2. 背景与结论（前两轮分析总结）

### 2.1 结论一：qtoc_core 骨架是领域中立的，编码偏见集中在三处

**可复用的中立骨架**：会话持久化与回滚/分叉、事件流（`/event`）、工具执行框架、权限闸门、插件与 MCP 扩展、结构化输出（`format: json_schema`）、多 daemon 隔离、HTTP/SSE 协议。

**编码偏见来源**：

| 来源 | 说明 | 可否在架构下消除 |
|---|---|---|
| 内置 system prompt | `prompt/default.txt` 等按模型选择，身份是"software engineering" | **可以**：agent 的 `prompt` 字段整段替换内置提示（`packages/opencode/src/session/llm/request.ts:60`） |
| 内置工具集 | read/write/edit/bash/grep/glob/lsp 等全部面向本地代码 | **可以**：按 agent 关闭内置工具，仅保留领域工具（MCP/插件） |
| 文件/目录上下文模型 | 会话以 directory/location 为作用域 | **部分**：领域数据通过工具访问，`references`/`instructions` 可承载知识；文件语义不构成阻断 |

### 2.2 结论二：真正的硬伤不在 prompt 组装，而在数据授权、安全与编排

| # | 硬伤 | 结论 |
|---|---|---|
| 1 | 无数据级授权（RBAC/ABAC、行列级、PII） | 内核 `permission` 只到"工具+pattern"粒度 → **策略必须下沉到工具网关** |
| 2 | 敏感数据落盘/日志/事件无脱敏与保留策略 | → 专用部署 + 磁盘加密 + 工具只回传聚合/样本 + 会话保留策略 |
| 3 | LLM 非确定性 vs 规则需版本化/审批/复现 | → 模型只产出"草案/解释"，规则落库、由确定性引擎执行 |
| 4 | 无原生调度/批处理 | → 外部编排器驱动 daemon API，每任务一会话，幂等 messageID |
| 5 | 数据量与上下文限制（工具输出截断、压缩丢细节） | → **计算下推**，工具只回传句柄+统计+样本 |
| 6 | 领域工具缺失 | → MCP/插件工具补齐，不属于硬伤 |
| 7 | 多租户/身份薄弱（单 Basic Auth） | → 一租户一 daemon + 上游网关鉴权 |
| 8 | 产物管理缺失 | → 工具写回外部系统并返回引用 ID |

### 2.3 核心设计原则（由上述结论导出）

1. **确定性下沉**：校验、执行、格式化、质检全部由确定性工具完成；模型只负责理解、生成、修复与解释。
2. **概率环节有界**：生成与修复回路必须有重试上限、差异检查与升级路径。
3. **数据不出域**：原始数据留在数据平面，模型侧只见到结构、统计与受控样本。
4. **扩展只用稳定点**：agent 配置 + MCP/插件工具 + 结构化输出 + `question` 工具；实验钩子隔离使用并锁定版本。
5. **内核零改动优先**：任何领域能力不得要求修改 `packages/{core,server,opencode}`；若必须修改，按 KG 流程评估上游化。

**分层职责**

| 层 | 职责 | 明确不做 |
|---|---|---|
| Qt 壳 | 交互、澄清、展示、审批、追溯 | 不拼 prompt、不做数据授权、不解析模型原始输出 |
| qtoc_core | 会话/循环/事件/权限/压缩/插件宿主 | 不直连数据库、不实现领域规则 |
| 领域能力网关 | 领域工具、策略执行、计算下推、结果句柄、脱敏、审计 | 不持有会话状态、不生成自然语言 |
| 数据与规则平面 | 数据、语义、规则、契约、审计的真实来源 | 不感知模型 |
| 外部编排 | 批处理、调度、审批、评估 | 不绕过网关直连数据 |

## 4. 领域能力需求（功能需求）

编号 FR-x，按优先级 P0/P1/P2 标注。

### FR-1 语义层与模式目录（P0）

- 提供表/列/类型/主外键/枚举值/样例值/同义词/指标口径/负责人等元数据检索；
- 支持按业务术语召回候选表列（模式链接），返回相关性排序与置信度；
- 元数据来源：**优先 OpenMetadata**（选型与定制策略见 11.1）；网关保持"可替换元数据源"接口，并在检索排序、授权过滤、缓存失效、口径权威四个控制点自研增强。

### FR-2 示例检索（Q→SQL 记忆）（P1）

- 维护经审核的"业务问题→SQL"示例库（可含指标、口径、注意事项）；
- 生成前按问题相似度召回 Top-K，作为 few-shot 注入（经 `chat.message` 或工具结果）；
- 示例来源：人工沉淀 + 成功链路自动归档（需审批）。

### FR-3 SQL 治理校验（P0）

- AST 级校验：只读语句、表白名单、禁止 DDL/DML/系统表、强制 LIMIT、超时与成本上限；
- 方言检查与规范化；
- 可选 EXPLAIN 试跑（不返回数据），产出成本估计；
- 失败时返回**结构化错误**（错误类、位置、可修复提示）。

### FR-4 只读查询执行（P0）

- 只读账号 + 行级策略（由网关按调用者身份执行）；
- 超时、最大行数、最大字节数；
- **不返回全量数据**：返回结果句柄（handle）+ 列元信息 + 统计 + 受控样本（≤N 行）；
- 结果临时存储在数据平面，句柄带 TTL 与访问控制。

### FR-5 输出格式化与契约校验（P0）

- 按"输出契约"（JSON Schema + 字段映射 + 枚举归一 + 类型转换 + 排序/精度规则）将结果句柄转为固定格式；
- 返回 `{ artifact, schemaReport }`；契约不满足时返回结构化违规清单；
- 契约版本化，查询请求需指定 `contractId`。

### FR-6 数据质量检查（P0）

- 规则包（版本化）驱动：非空率、唯一性、值域、参照完整性、行数区间、新鲜度、分布/波动、跨表一致性；
- 阈值可配置、可按维度分组；
- 返回 `{ passed, violations[{rule, severity, dimension, detail}] }`；
- 质检在**结果句柄**上执行，不回传原始数据。

### FR-7 修复回路控制（P0）

- 失败分类（见 5.3）与修复简报（结构化：原问题、SQL、失败类、违规项、提示、历史尝试）；
- 有界重试（默认 ≤3）、差异检查（SQL 未变化则不再重试）、不可修复类快速失败；
- 原始业务描述在会话中"钉住"（压缩保护），确保多轮修复不丢上下文。

### FR-8 歧义澄清（P1）

- 模式链接置信度低、指标口径歧义、缺少时间范围/过滤条件时，使用内核 `question` 工具向用户提问；
- 澄清结果写入会话，作为后续修复的权威约束。

### FR-9 审计与可观测（P0）

- 每次链路执行产出审计记录：请求者、会话 ID、业务描述、候选模式、每轮 SQL、校验/执行/质检结果、重试次数、最终状态；
- 通过 `/event` 采集，落外部审计存储；
- 指标：一次通过率、平均修复轮次、不可修复占比、端到端时延、成本。

### FR-10 契约与规则注册（P1）

- 输出契约、指标口径、质量规则包统一注册、版本化、审批后生效；
- 查询与质检结果记录所用契约/规则版本，保证可复现。

### FR-11 批处理与调度集成（P2）

- 外部编排器通过 `POST /session` + `prompt_async` + `/event` 驱动批量任务；
- 每表/每案件一个会话；`messageID` 幂等；失败任务可重放；
- 与交互式链路共用同一网关与契约。

### FR-12 评测与回归（P1）

- 金标集：业务描述 → 期望 SQL 结构/结果断言/质量结论；
- 每次升级内核、提示词、工具或模型后自动回归；
- 输出准确率、修复率、越权拦截率等指标。

## 5. 样例链路设计：Text-to-SQL 治理闭环（宏观）

### 5.1 状态机

```
[0] 接入      业务描述 + contractId + 执行上下文（租户/时间范围/权限）
      │
[1] 澄清      question：口径/时间/维度不明确 → 先问不猜（FR-8）
      │
[2] 链接      schema.search + examples.retrieve → 候选表列/指标/示例
      │
[3] 生成      结构化输出 { sql, assumptions[], tables[], confidence }
      │
[4] 校验      sql.validate（策略/方言/EXPLAIN）
      ├─ A 类失败 ──► 修复
      ▼
[5] 执行      sql.execute → resultHandle + stats + sample
      ├─ B 类失败 ──► 修复
      ▼
[6] 格式化    result.format(handle, contract) → { artifact, schemaReport }
      ├─ C 类失败 ──► 修复
      ▼
[7] 质检      quality.check(handle, rulePack) → { passed, violations }
      ├─ D 类失败 ──► 分类后修复
      ▼
[8] 交付      固定格式结果 + 质检报告 + SQL + 血缘 + 假设说明 + 审计
      └─ 达上限/不可修复 ──► 升级：最佳结果 + 报告 + 人工介入
```

### 5.2 时序（交互式单会话）

```
Qt             qtoc_core(agent)          网关(工具)              数据平面
│ 业务描述 ──────►│                          │                      │
│                │ schema.search ──────────►│ 目录检索 ────────────►│
│                │◄──── 候选表列/指标 ───────│◄─────────────────────│
│                │ (必要时 question → Qt)     │                      │
│                │ 生成 SQL（结构化输出）      │                      │
│                │ sql.validate ───────────►│ AST/策略/EXPLAIN ────►│
│                │◄──── ok/结构化错误 ───────│                      │
│                │ sql.execute ────────────►│ 只读执行+策略 ───────►│
│                │◄──── handle+stats+sample ─│◄─────────────────────│
│                │ result.format ──────────►│ 契约映射 ────────────►│
│                │◄──── artifact/schemaReport│                      │
│                │ quality.check ──────────►│ 规则包执行 ──────────►│
│                │◄──── passed/violations ───│                      │
│  [不合格] 修复简报 → 重新生成 SQL（≤3 轮，差异检查）              │
│  [合格] 结果+报告 ─►│                      │                      │
```

### 5.3 失败分类与修复策略

| 类 | 典型场景 | 可修复 | 策略 | 不计入重试的情形 |
|---|---|---|---|---|
| A 静态校验 | 方言错误、越权表、缺 LIMIT、成本超限 | 模型 | 带结构化错误与规范重生成 | 越权/策略拒绝（安全事件，直接失败并告警） |
| B 执行 | 列不存在、类型不匹配、除零、超时 | 模型（超时除外） | 带错误码与 EXPLAIN 修复；超时降采样/加过滤 | DB 不可用、连接池耗尽 |
| C 格式 | 缺列、类型不符、枚举未归一 | 模型/格式化器 | 先判"SQL 形状错"（模型修）还是"映射缺失"（修契约） | 契约本身无解（需人工） |
| D 质量 | 空结果、主键重复、值域越界、null 超阈、行数异常 | 视根因 | 查询逻辑问题→模型修；数据本身问题→输出报告不重试 | 数据源无数据、规则阈值不适用 |
| E 不可修复 | 权限不足、口径矛盾、契约冲突 | 无 | 快速失败，返回证据与建议 | 全部 |

**修复简报（结构化，模型输入）**

```json
{
  "attempt": 2,
  "originalQuestion": "……（钉住不压缩）",
  "previousSql": "SELECT ...",
  "failureClass": "D",
  "violations": [{ "rule": "uniqueness", "severity": "high", "detail": "order_id 重复 12 行" }],
  "schemaHints": ["orders.order_id 为主键", "orders.status 枚举：paid/refunded"],
  "constraints": ["只读", "必须 LIMIT ≤ 10000", "时间范围 2026-01-01 起"],
  "instruction": "仅修复导致违规的查询逻辑，保持已确认口径不变"
}
```

### 5.4 收敛与升级规则

1. 重试上限 3；每轮 SQL 必须与上一轮不同（归一化后比较），否则立即升级；
2. 同一失败类连续 2 次未消除 → 升级（附完整尝试历史）；
3. 升级出口：返回最佳结果 + 质量报告 + SQL + 失败原因；Qt 侧提供人工修正与"存为示例/规则"入口；
4. 成功链路可选归档为示例（FR-2），需审批。

## 6. 与 qtoc_core 的边界映射（扩展点选型）

| 需求 | 内核扩展点 | 形式 | 稳定性 |
|---|---|---|---|
| 领域身份/行为 | agent `prompt`（整段替换）、`temperature`、`steps`、`model` | 配置（`OPENCODE_CONFIG_CONTENT`） | 稳定 |
| 工具白名单/闸门 | agent `permission`（`tools` 已废弃） | 配置 | 稳定 |
| 领域工具 | MCP（local/remote）或插件 `tool` | 外部服务 / in-process | 稳定 |
| 工具级策略 | 插件 `tool.execute.before/after`、`tool.definition` | 插件 | 稳定 |
| 权限决策外置 | 插件 `permission.ask`（可接 OPA/Casbin） | 插件 | 稳定 |
| 结构化输出 | prompt body `format: { type: "json_schema", schema }` | 协议 | 稳定 |
| 歧义澄清 | 内置 `question` 工具（需 `OPENCODE_CLIENT=desktop`） | 协议/配置 | 稳定 |
| 上下文注入 | `instructions`、`references`、`skills`、`commands` | 配置/文件 | 稳定 |
| 每轮注入/改写 | 插件 `chat.message`（持久化）、`experimental.chat.messages.transform`、`experimental.chat.system.transform` | 插件 | 实验（需锁定） |
| 压缩保护 | 插件 `experimental.session.compacting` | 插件 | 实验（需锁定） |
| 审计/事件 | `GET /event`、`POST /log` | 协议 | 稳定 |
| 多租户隔离 | 每租户一 daemon：`OPENCODE_DB`/`XDG_*`/随机端口与密码 | 部署 | 稳定 |

**关键约束**：

- 长耗时查询不要走 MCP 默认 5s 超时（`ConfigMCPV1.Local.timeout`，默认 5000ms），需显式调大；或使用插件工具（in-process，但禁止阻塞事件循环，重活放外部进程/线程）。
- 结果集不进模型上下文：统一"结果句柄"模式，规避工具输出截断与压缩丢失。
- 业务凭据只存在于网关，绝不写入 `OPENCODE_CONFIG_CONTENT` 的 prompt 或会话消息。

## 7. 与 OpenCode 同步发展的兼容策略

1. **零内核改动**：领域能力全部在配置、插件、MCP、外部服务中实现；`qtoc:trim` 仅维护既有发行定制。
2. **扩展点分层锁定**：
   - 一级（稳定，可放心依赖）：agent 配置、MCP、`format`、`question`、`permission`、`/event`、插件 `tool` 与 `tool.execute.*`；
   - 二级（实验，隔离并回归）：`experimental.chat.system.transform`、`experimental.chat.messages.transform`、`experimental.session.compacting`——集中在单个适配插件内，随内核版本锁定，升级时跑契约测试。
3. **协议面纪律**：只用稳定面（`/session`、`/event`、`/permission`、`/question`、`/config`、`/config/providers`）；不依赖 `/api/*` 与 `/experimental/*`。
4. **升级流程**：`bun run qtoc:sync` → 构建 → 领域回归（FR-12 评测集）→ 契约 diff（`openapi.json` 与事件联合类型）→ 更新适配插件与文档。
5. **失败兜底**：插件异常必须降级为"不注入/不拦截"，不得使会话失败（参考 `methodology.md` 5.4 约束）。

## 8. 非功能需求

| 维度 | 要求 |
|---|---|
| 安全 | 数据级授权在网关执行；凭据不出网关；按 agent 禁用 shell/webfetch；SQL 只读与白名单强制；敏感结果脱敏后仅回样本 |
| 合规 | 会话/审计数据加密落盘、保留期可配；支持按租户独立 daemon 与数据驻留 |
| 审计 | 每次链路执行可完整还原（输入、候选、SQL、校验、执行统计、质检、重试、结论、版本） |
| 性能 | 单次交互 P95 ≤ 30s（不含用户澄清）；批量任务吞吐由外部编排控制；网关工具并发与连接池独立治理 |
| 可用性 | 网关/数据源故障快速失败（E 类），不进入重试循环；daemon 崩溃自愈（Qt 侧重启） |
| 可观测 | 指标（FR-9）+ 结构化日志 + 事件外送；告警阈值（越权拦截、修复率骤升、超时率） |
| 兼容 | 内核升级不改变网关契约；网关版本与契约/规则版本可独立演进 |
| 可测试 | 金标集回归 + 契约测试（http-recorder）+ 修复回路仿真 |

## 9. 部署与多租户模型

| 场景 | 拓扑 | 隔离手段 |
|---|---|---|
| 单团队/单域 | 单 daemon + 单网关 | `x-opencode-directory` 区分项目 |
| 多租户/多密级 | 每租户（或每密级）一个 daemon + 独立网关 | `OPENCODE_DB`、`XDG_*`、随机端口与密码、独立凭据与策略 |
| 混合 | 公共 daemon（低敏）+ 独立 daemon（高敏） | 敏感域禁网、禁 shell、独立审计 |

部署建议：内核与网关同机部署（本机回环通信）；数据平面凭据由密钥管理服务注入网关；审计经网关直写外部存储（不依赖内核日志）。

## 10. 路线图与验收

| 阶段 | 交付物 | 验收标准 |
|---|---|---|
| P0 MVP | 领域 agent 配置 + 语义层检索 + 校验/执行 + 固定契约输出 | 单表/单指标端到端跑通；越权 SQL 100% 拦截；结果不含原始全量数据 |
| P1 闭环 | 质量引擎 + 修复回路 + 审计 | 一次通过率 ≥ 基线；平均修复轮次 ≤ 1.5；不可修复占比可解释；审计可完整还原 |
| P2 增强 | 歧义澄清 + 示例检索 + 契约/规则注册 | 人工干预率下降；SQL 正确率在金标集上提升；契约/规则版本可追溯 |
| P3 规模化 | 批处理编排 + 评测回归 | 批量成功率达标；内核升级后回归不退化；无内核 delta |

**北极星指标**：一次通过率（无需修复即合格）、修复收敛率（≤3 轮内合格）、不可修复率、越权/违规拦截率、端到端时延与单次成本。

## 11. 决策记录与语义层定制

> 本节将原"开放问题"固化为决策（2026-09-20），并给出语义层的选型与定制设计；决策记录同步见 `../KG/data-agent-faq.md`。

### 11.1 语义层：OpenMetadata 优先 + 定制异化能力

#### 11.1.1 三种方式对比

| 维度 | DataHub | OpenMetadata | 自建 |
|---|---|---|---|
| 定位 | 元数据图与血缘平台（LinkedIn 起源，Apache 2.0） | 目录 + 质量 + 剖析一体化平台（Apache 2.0） | 面向检索的最小注册表 |
| 血缘 | 表级 + 列级，生态最深，影响分析强 | 表级 + 列级，够用 | 无（需自研） |
| 数据质量 | Assertion/Incident，相对新 | **原生测试框架 + Profiler**（null/distinct/min/max/直方图） | 需自研规则引擎 |
| 治理/分类 | Domain/Glossary/Tag/Contract/Owner | Glossary/Classification（含 **PII 自动分类**）/Contract/Team | 仅保留必要字段 |
| 部署 | 重（Kafka + ES + GMS + UI + 存储） | 相对轻（API Server + OpenSearch + 存储） | 最轻 |
| AI/Agent | 官方 MCP server | MCP server + 商业版 AI | 自建 MCP |
| 适用 | 血缘/影响分析刚需、有平台团队 | 目录与质量并重、平台团队有限 | MVP、数据源少、单团队 |

#### 11.1.2 决策

**优先 OpenMetadata**，理由：本链路的核心是"格式 + 质量检查"闭环，OpenMetadata 的原生 DQ/Profiler/PII 分类/契约与 FR-5/FR-6 高度重合；部署与运维成本低于 DataHub；API-first 便于网关集成与定制。已有 DataHub 投入的组织直接集成，网关保持元数据源可替换。P0 允许以自建最小注册表快速验证，但接口按可替换设计。

#### 11.1.3 定制异化能力（嵌入 / 控制 / 修改）

**原则：定制只落在扩展点，不改核心；所有定制必须能在 OpenMetadata 升级后存活。**

| 层次 | 定制点 | 方式 | 升级风险 |
|---|---|---|---|
| L1 无侵入 | 自定义属性（Custom Properties）、Glossary、Tag/Classification、Domain、Owner、契约 | OpenMetadata API/UI 定义，不改 schema | 无 |
| L2 官方扩展 | 自定义 ingestion connector、自定义 DQ 测试定义（test definitions）、Webhook | 官方扩展机制（Python 插件） | 低 |
| L3 网关自研 | 语义检索与重排、同义词/示例库、授权与密级过滤、缓存与失效、口径双写 | 网关侧实现，只消费 OM API/事件 | 无（与 OM 解耦） |
| L4 薄 fork | 必须修改 OM 源码的能力（如特殊实体模型、特殊 UI） | 独立分支 + 最小 patch 集 + 定期 rebase；禁止直接改主分支 | 高（最后手段） |

**四个必须自研的控制点**（对应"嵌入或控制"）：

1. **检索质量**：网关自建向量索引（术语、列注释、Q→SQL 示例），不依赖 OM 搜索排序；OM 只作为权威元数据源；
2. **授权与密级**：OM 提供分类（PII/密级）元数据，**过滤与行列级策略在网关执行**；OM 不接触业务凭据；
3. **缓存与漂移**：网关缓存 OM 实体版本（schema/指标/分类），通过 Webhook/变更事件驱动失效，TTL 兜底；
4. **口径权威**：指标口径在 OM Glossary 与契约库**双写**，以审批流版本为准，网关按版本号取用。

**升级护栏**：

- OM 版本 pin（记录在部署清单），升级走独立窗口 + 网关契约测试；
- 网关对 OM 的 API 依赖面收敛到少数接口（实体读取、搜索、血缘、测试结果、Webhook），禁止散落调用；
- L4 薄 fork 仅在 L1–L3 无法满足时启用，且必须记录 patch 清单与 rebase 责任人（KG 流程）。

#### 11.1.4 同步频率

| 数据类 | 频率 | 触发方式 |
|---|---|---|
| 结构（表/列/类型/主外键） | 每日全量 + 增量事件 | 定时 + DDL/CDC/Webhook；网关缓存 TTL 10–30 分钟，失效事件即时清除 |
| 口径（指标/术语/同义词） | 审批后即时 | 审批流发布即推送 |
| 示例（Q→SQL） | 审批后即时 + 每日重建索引 | 成功链路归档需审批；向量索引每日重建 |
| 血缘/负责人 | 每日 | 定时（对生成链路非关键，可放宽） |
| DQ 测试结果 | 每次执行后 | OM Webhook → 网关；用于质检规则校准与告警 |

### 11.2 输出契约：平台管框架、业务管内容

| 角色 | 职责 |
|---|---|
| 业务/领域方 | 编写契约内容：字段映射、枚举归一、精度/排序、业务校验说明 |
| 平台方 | 契约框架与注册中心、JSON Schema 校验、CI 校验、PII 密级标注、版本与兼容性规则、发布审批 |

强制约束：契约**不可变版本化**；查询必须携带 `contractId + version`；被引用版本禁止原地修改；新版本需通过金标集回归。原则：**平台做护栏，领域做作者**。

### 11.3 修复回路：单会话 vs 外部编排

| 场景 | 形态 | 判据 |
|---|---|---|
| 交互式 | 单会话（模型自修复） | 有人等待、需要澄清、单条查询、延迟预算 < 60s、重试 ≤ 3 |
| 批量 | 外部编排（分阶段调用） | 无人等待、定时触发、单批 ≥ 50 条、需严格审计/幂等/成本上限/并行 |
| 混合 | 共用网关工具与契约；编排器按阶段调 `prompt_async`，每任务一个会话 | 批量但偶需人工复核 |

硬规则：**无人等待 + 单批 ≥ 50 条 + 要求可重放** → 外部编排；否则单会话。达到任一条件即切换，不做主观判断。

### 11.4 质检规则：三角色、两级审批

| 角色 | 职责 |
|---|---|
| 规则作者（数据管家） | 编写规则、阈值依据、适用范围，绑定指标口径 |
| 规则审批人（领域负责人/治理委员会） | 审批发布、决定严重级别与例外放行 |
| 平台 | 注册中心、版本化、可执行性校验、冲突检测、回归基线、发布后监控 |

流程：`草稿 → 同行评审 → 领域负责人批准 → 发布（不可变版本） → 下线（带 sunset）`。每条规则必须带责任人、严重级、适用条件、阈值理由、复核周期、告警路由；例外（waiver）必须有到期时间并审计；规则变更必须重跑金标集校准。

### 11.5 内核级"数据上下文源"：暂不引入

**理由**：数据上下文大且动态，按需检索（工具）优于常驻系统提示；内核改动破坏零 delta 与上游同步；`experimental.chat.system.transform` 已可注入"小而稳定"的上下文。

**复查触发点**（任一满足则重新评估，按 KG 流程评估上游化）：

1. 出现每次请求都必须存在的稳定上下文（如租户策略摘要），且插件注入被证明 token/缓存成本不可接受；
2. 合规要求对"上下文变更"做内核级审计；
3. 上游将 System Context 开放为公共扩展 API（接入成本显著下降）。

### 11.6 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 语义层质量不足 | 模式链接错误是最大失败源 | P0 先做元数据治理；低置信度强制澄清 |
| 质量规则与业务口径不一致 | 假失败导致无效重试 | 规则审批 + 金标集校准；规则版本化 |
| OpenMetadata 升级/定制漂移 | 网关集成失效 | L1–L3 定制、版本 pin、API 依赖面收敛、契约测试；L4 薄 fork 记录 patch 清单 |
| 实验钩子变更 | 注入/压缩保护失效 | 隔离到单一适配插件 + 版本锁定 + 回归 |
| MCP 超时/长查询 | 执行失败率上升 | 显式超时配置 + 异步执行 + 句柄轮询 |
| 多租户资源竞争 | 相互影响 | 独立 daemon/网关 + 配额 |
| 模型成本 | 批量场景成本失控 | 模型路由（小模型做链接/修复）+ 缓存 + 批处理限额 |
| 结果缓存与一致性 | 脏读/口径漂移 | 契约/规则版本入缓存键；TTL 与失效策略 |

## 12. 附录

### A. 术语

| 术语 | 含义 |
|---|---|
| 语义层 | 表/列/指标/同义词/示例的受治理元数据集合 |
| 模式链接 | 将业务术语映射到候选表/列/指标的过程 |

| 失败分类 | A 静态校验 / B 执行 / C 格式 / D 质量 / E 不可修复 |
